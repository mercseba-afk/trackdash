## Safe sequence and rollback

1. Obtain compliant, usable destination and explicit approval for protected extraction/import; validate Free eligibility, usable Auth/REST and provider configuration. Rehearse the full matrix there with synthetic users/objects and existing tools. Current temporary staging is not assumed authorized/usable. Price both migration traffic and stored backup size against remaining quotas before extraction.
2. Approve a bounded write freeze and rollback window. Drain existing workers; stop duplicate scanner/cron execution only under that future approval, preserving cadence configuration. Freeze app/API/Auth/Storage/direct-writer mutations and verify no in-flight writers. **eBay deletion intake needs a proven lossless handoff**: any accepted deletion after a snapshot must be represented in the final destination before serving it; incomplete requests must remain recoverable. Finite provider retries are not a durable journal. Current P0.8 has no independent intake journal/tombstones, so an unproven freeze/handoff remains a migration blocker. Do not integrate #430 automatically or claim this solved by P0.9.
3. Export a fresh consistent snapshot, all associated objects and configuration; import atomically using the approved managed-schema/key procedure, re-enable native triggers/publications and validate every gate. Do not use a pre-erasure backup. Independent post-snapshot erasures/new writes must be reconciled before cutover; retaining an old source is not permission to expose resurrected identifiers.
4. On the destination **before app deployment** apply unchanged `proposals/p08-ebay-erasure.sql`: helper transaction → five CREATE INDEX CONCURRENTLY outside any outer transaction → RPC/EXECUTE grants and PostgREST reload. Verify all five valid/ready indexes, role-only RPC access, native RLS/triggers/queue unchanged and old-app compatibility. Interrupted stages are inventoried/resumed, never blindly re-run. Do not place these concurrent indexes inside the restore transaction.
5. After matrix PASS and explicit deployment approval: securely configure target Vercel env/OAuth, build the approved combined #432+P0.9 SHA once and switch traffic. Only one authoritative DB and scheduler. Check `/api/version`, IT/EN pages, Auth/API and privacy boundaries. Record the exact point at which target writes are enabled. No merge or deploy to the restricted source on the way.
6. Before target writes, revert app/env/routing only if source is actually usable and unchanged. After target writes, **do not point back to a stale source**: freeze again and reconcile/export the authoritative latest data/objects/erasures/Auth state, or roll back app code while retaining the new DB. A source still returning 402 is not a working rollback destination. Retain P0.8 indexes/RPC/grants, all redactions and recompute jobs for application rollback. Never restore a prior backup as an erasure rollback.
7. Observe 48h then 7d; only after stable evidence and explicit approval retire old credentials/projects/backups. Keep encrypted backup retention minimal and document deletion reapplication obligations. Free has no native backup/PITR safety net; P0.8's post-commit reintroduction, exhausted pre-commit retries and pre-erasure restore risks are preexisting and unresolved. They are especially relevant to an actual migration and cannot be waived by local tests.
